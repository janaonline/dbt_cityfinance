# Folder structure

Reference for what lives where in this repo. See [architecture.md](architecture.md) for *why* things are organized this way and how data flows through them.

## Top level

```
.
├── CLAUDE.md              # Project-wide instructions for Claude Code
├── dbt_project.yml        # Project config: paths, schema/tag/materialization routing per module
├── packages.yml            # Declared package deps (dbt_utils, dbt_expectations, elementary)
├── package-lock.yml         # Resolved package deps incl. transitive (generated by `dbt deps`)
├── profiles.yml            # Local dev DB connection — gitignored, never commit, not present in prod
├── .gitignore
├── .user.yml               # dbt-generated anonymous usage-tracking id (not a config file)
├── models/                 # One folder per business module — see below
├── macros/                 # Project-wide Jinja macros (3 total, see architecture.md)
├── seeds/                  # CSV seed data — only iso_codes.csv currently
├── analyses/               # dbt analysis-paths target — currently empty (.gitkeep only)
├── snapshots/              # dbt snapshot-paths target — currently empty (.gitkeep only)
├── tests/                  # dbt test-paths target (singular/custom SQL tests) — currently empty (.gitkeep only)
├── docs/                   # This documentation
└── .claude/
    ├── settings.local.json # Local permission overrides — gitignored, may hold credentials, never commit
    └── skills/              # Claude Code Skills for this repo — see below
```

`logs/`, `target/`, `dbt_packages/`, `venv/` also exist locally but are dbt/tooling-generated and gitignored — not part of the source layout.

## `models/` — one folder per business module

Every module folder follows the same shape, but **not every module has every piece**:

```
models/<module>/
  source.yml       # always present — source table declarations
  schema.yml        # optional — column/model tests (only 2 of 9 modules have one)
  staging/          # optional — thin cleanup/rename models (only 1 of 9 modules has one)
  marts/            # always present — final business-logic models
```

Current inventory (verified against the filesystem):

| Module | `source.yml` | `schema.yml` | `staging/` | `marts/` files |
|---|---|---|---|---|
| `property_tax_poc` | yes | yes | yes (4 files) | 6 |
| `grants_condition` | yes | no | no | 7 |
| `grants_allocation` | yes | no | no | 2 |
| `ap_api_poc` | yes | no | no | 4 |
| `afs_digitisation_tracker` | yes | no | no | 6 |
| `afs_analysis` | yes | no | no | 2 |
| `market_readiness` | yes | no | no | 1 |
| `nmam_ulb_response` | yes | no | no | 1 |
| `cf_municipal_finance_rt` | yes | yes | no | 4 |

`property_tax_poc` is the only module with a full staging layer:
```
models/property_tax_poc/staging/
  stg_growth_rate.sql
  stg_population_data.sql
  stg_tax_sub_rate.sql
  ulbs_in_state.sql
```

`models/afs_analysis/` also contains a stray `.DS_Store` (macOS artifact — untracked/ignored via the project's existing `.gitignore` `.DS_Store` rule; a separate `.DS_Store` at the repo root is already tracked in git history from before that rule existed, so it remains as-is).

## `macros/`

```
macros/
  generate_schema_name.sql   # overrides dbt's default schema-name macro
  safe_numeric.sql           # cleans/validates/casts messy numeric strings
  design_year_minus.sql      # subtracts n years from a 'YYYY-YY' design-year string
  .gitkeep
```

No other macros exist. See [architecture.md](architecture.md) for behavior and usage sites.

## `seeds/`

```
seeds/
  iso_codes.csv
  .gitkeep
```

Only one seed file. No seed-level `schema.yml`, `column_types`, or tests — all seed config is the single `+schema: cf_prod` block in `dbt_project.yml`.
